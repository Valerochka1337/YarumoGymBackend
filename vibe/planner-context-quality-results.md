# Calendar context v2 — локальный результат

База origin/main: 285f222. Worktree `/private/tmp/ValerochkaGymBackend-planner-context`,
ветка `feat/planner-context-quality`. Изменяется только backend.

## Что передаётся

- Три последних завершённых родителя с реальными start/finish в выбранной зоне,
  количеством выполненных подходов внутри/вне окна и сгруппированными одинаковыми
  результатами. Группировка сохраняет количество, но не порядок подходов внутри занятия.
- Actual weight/reps/duration/speed/incline с единицами в ключах, setType,
  явными null и пометками legacy/fallback completion time. Причины пропуска не выводятся.
- Остальная история за 28 локальных дат — четыре непересекающиеся недельные сводки
  количества подходов по exerciseId и суммы contribution points по мышцам.
  Contribution points — арифметика текущего каталога, не «эффективные подходы».
- Последние два наблюдения упражнения-кандидата: opaque observationId с единственным
  определением в recent detail или additional observations, даты и давность вычисляет сервер.
  Дополнительные наблюдения не добавляют объём. Разные exerciseId никогда не объединяются.
- Для длинного перерыва — максимум три последних завершённых родителя до окна.
  Это не поиск последнего выполнения каждого упражнения за всю жизнь. Старые факты
  отделены от месячной нагрузки и НЕ поступают в прежнюю функцию назначения веса.
- История не содержит снимков типа/оборудования упражнения. Поэтому числовые изменения
  не объявляются прогрессией/рекордами; модель видит наблюдения и ограничение сопоставимости.

## Отбор и бюджет

Существующие gym intersection, equipment/exercise exclusions и допустимые типы применяются
до сокращения. Архивные standard rows отсекаются capture; selector также защищён от archived
payload. Неизвестные требования к оборудованию теперь явно обозначены UNKNOWN.

В набор входят все знакомые упражнения из ограниченного capture, первые две альтернативы
для каждой мышцы/типа и комбинации оборудования/типа. Далее он дополняется до 36:
это три кандидата на максимальные 12 мест ответа, инженерный стартовый запас, не
доказанный физиологический оптимум. Порядок: существующие goalGroup, priority, coverage,
затем exerciseId. Отбор детерминирован, не использует экспоненциальное затухание.
Если представительство требует больше 36 (в тесте >60), набор расширяется.
При свободных preferences/currentState/manualConstraints сохраняется весь eligible catalog:
без дополнительного NLP нельзя гарантировать сохранение названного пользователем варианта.

Удалены повторяющиеся per-candidate `available=true` и `coverage` из запроса.
Coverage остаётся только внутренним существующим tie-breaker, не инструкцией выбирать
все ненагруженные мышцы. Notes hints ограничены выбранными кандидатами.

Пределы чтения: прежние <=1000 effective exercises, <=64 родителей окна, дополнительно
<=3 старых родителей; <=8192 факта каждой части (всего <=16384); <=1 MiB на исходную
строку, <=8 MiB на capture. Размеры родителей проверяются до payload hydration.
Оба history key query используют существующий partial index (проверено EXPLAIN).
Контекст модели <=262144 UTF-8 bytes; превышение даёт `ai_context_too_large` до provider,
не скрытое обрезание ограничений. Инструкция и неизменная output schema учитываются
отдельно в измерениях. Количество токенов не измерено.

## Контракт и проверяемость

Output schema, допустимые IDs/типы/числа, known-duration lower bound, веса, очередь,
idempotency, freshness/owner fencing, journal и явное подтверждение сохранены.
В существующем строгом Calendar output нет explanation/evidence поля. Нового UI/протокола
не добавлено; инструкция запрещает маскировать объяснение в name. Следовательно,
проверенного сервером объяснения выбора в этом выпуске нет. Opaque IDs используются
только для внутриконтекстных ссылок, которые строит сервер; LLM не возвращает эти ссылки
или фактические числа истории. Не заявляется проверка произвольного текста LLM.

## Синтетические сценарии

| Сценарий | Проверяемое ожидание / неприемлемый вывод |
|---|---|
| Нет истории | null last finished, NO_OBSERVATION_IN_CAPTURE; не «никогда не тренировался» |
| Регулярные занятия | recent + weeks точно разделяют нагрузку; refs не добавляют подходы |
| Длинный перерыв | максимум 3 старых родителя, давность, нулевой месячный вклад старых фактов |
| Недавние повторы | группировка сохраняет count; нет запрета повторять упражнение |
| Исправленная история | новые actual видны после capture; удалённые/активные записи исключены |
| Мало времени | сохраняются 10 минут intent; existing validation отклоняет превышение known duration |
| Смена зала | только соответствующий gym intersection, UNKNOWN не становится bodyweight |
| Жёсткие исключения | знакомое исключённое упражнение не возвращается через shortlist |
| Большой каталог | 1000 -> 36 для однородного fixture; знакомые/редкие альтернативы сохранены |
| Архив/удаление | archived payload/catalog gyms и deleted workouts не проходят |
| Старые факты | не назначают устаревший вес; не смешиваются с месячным объёмом |
| Разные типы | STRENGTH/TIMED/CARDIO остаются разными, unknown comparability явна |

Byte comparison воспроизводится тестом `CalendarPlannerContextTest` в
`build/reports/planner-context/bytes.md`. Envelope v1 взят из 285f222; для большого fixture
baseline закреплён 227166 bytes. Одинаковые синтетические входы, без AI/provider network.
Восемь payload-сценариев измеряются; остальные hard-filter/DB сценарии проверяются тестами.

## Границы доказательств

Тесты подтверждают полноту переданных полей в заданном capture, partition/счёт, ограничения,
детерминизм и размер. Независимое read-only review owner/consent/numeric scope дефектов
не выявило. Это не измерение физиологического качества плана или задержки провайдера.
Реальных AI-запросов, секретов, production, телефона/браузера/скриншотов не использовали.

Для будущего отдельно разрешённого AI-eval: одинаковые синтетические сценарии v1/v2,
слепая оценка соблюдения ограничений, преемственности, уместности изменений, обращения
с неизвестными данными и реалистичности времени. Не требовать единственный «правильный»
список упражнений. Сравнивать несколько запусков и ошибки, не только удачный пример.
